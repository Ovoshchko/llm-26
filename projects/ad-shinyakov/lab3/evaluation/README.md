# Оценочный набор и сравнение

Набор содержит 18 задач для диагностики и восстановления приложений Kubernetes.
Формат задач включает входные сообщения, ожидаемые результаты, проверки состояния
и метаданные, необходимые для сравнения агентов.

## Файлы

| Файл | Назначение |
|---|---|
| [tasks.json](tasks.json) | Массив задач и эталоны проверки |
| [scenarios.json](scenarios.json) | Начальные состояния и события тестового стенда |
| [context.json](context.json) | Общие лимиты контекста и параметры токенайзера |
| [validation.json](validation.json) | Результаты проверки набора |

## Формат задачи

В tasks.json хранится массив объектов со следующими полями:

| Поле | Содержимое |
|---|---|
| `id` | Уникальная метка задачи для отчётов и трассировки |
| `input` | Массив пользовательских реплик в порядке выполнения |
| `expected_output` | Ожидаемый результат и критерии для проверяемых реплик |
| `state_checks` | Проверки состояния после тех же реплик |
| `metadata.type` | single или dialogue |
| `metadata.difficulty` | easy, medium или hard |
| `metadata.history_dependent_turns` | Номера реплик, ответ на которые зависит от предыдущей истории |
| `metadata.scenario_id` | Сценарий начального состояния из scenarios.json |
| `metadata.expected_tools` | Необходимые инструменты для проверяемых реплик |
| `metadata.reference_documents` | Эталонные документы для retrieval |

Реплики нумеруются с 1. В expected_output, state_checks и expected_tools ключи
являются строковыми номерами реплик. Присутствие номера в expected_output означает,
что ответ на эту реплику оценивается. У всех трёх полей должны совпадать номера.
Дополнительный список проверяемых реплик не хранится.

Например, в диалоге из 15 реплик expected_output может содержать ключи `"1"`, `"2"`
и `"15"`. Все реплики input передаются агенту последовательно, но оцениваются
только эти три ответа. Собственные ответы агента и результаты инструментов
сохраняются в одной диалоговой сессии.

expected_output содержит текстовый эталон вместе с критериями. Дословное совпадение
не требуется. История отмечается списком номеров без отдельной разметки каждого
сохраняемого факта. Ожидаемые инструменты задают необходимые возможности,
а не фиксированный порядок или точное число вызовов.

## Проверки состояния

state_checks — массивы декларативных проверок, сгруппированные по номерам реплик.
Ключ predicate определяет проверяемое условие; остальные поля задают объект
и ожидаемое значение.

| predicate | Условие |
|---|---|
| `mutation_count` | Количество фактически принятых изменений агента |
| `deployment_ready_replicas` | spec.replicas и readyReplicas равны заданному числу; контроллер обработал текущую generation |
| `deployment_unchanged` | Значимые поля спецификации и Pod UID контрольной нагрузки не изменились |
| `deployment_pods_replaced` | Исходные Pod заменены, новые реплики готовы |
| `deployment_template_unchanged` | spec.template не менялся, даже если изменялось число реплик |
| `deployment_image_unchanged` | Образы контейнеров остались прежними |
| `application_config_version` | Startup logs всех текущих реплик подтверждают заданную версию конфигурации |
| `rollout_incomplete` | Перезапуск принят, но обновлённые реплики не стали готовы в пределах времени ожидания |

Пример проверки после второй реплики:

```json
"state_checks": {
  "2": [
    {
      "predicate": "deployment_ready_replicas",
      "namespace": "agent-lab",
      "name": "worker",
      "equals": 4
    }
  ]
}
```

Изменения считаются накопительно в пределах одной задачи. Ошибка ответа инструмента
не отменяет уже принятую операцию. Действия самого стенда в счётчик не входят.
Сравнение неизменности ресурсов игнорирует resourceVersion, временные метки
и обычные обновления status. Для завершения Pod допускается ограниченное ожидание,
указанное в scenarios.json.

## Подготовка и выполнение сценария

scenarios.json содержит 15 декларативных спецификаций: ресурсы, предусловия,
начальные наблюдения и изменения перед отдельной репликой. Некоторые сценарии
используются несколькими заданиями. Манифесты и выполнение этих условий относятся
к реализации стенда.

Перед независимой задачей или сменой агента начальное состояние восстанавливается,
а диалоговая сессия создаётся заново. Между репликами одной задачи сохраняются
состояние кластера и история. Сценарии выполняются последовательно. Если предусловия
не подтверждены, результат учитывается как ошибка подготовки стенда.

В a17 моделируется потеря ответа после фактического принятия перезапуска.
В a18 стенд обновляет конфигурацию и заменяет Pod перед второй репликой.
Обозначения old_pod и new_pod разрешаются в реальные имена после подготовки
и не передаются модели в качестве имён Pod.

## Данные, доступные агенту

Общие ограничения стенда описаны в [документации проекта](../README.md).
Агент получает эти правила, описания инструментов и очередную пользовательскую
реплику. Фактическое состояние кластера он получает через инструменты.
Доступные сведения должны совпадать у собственного и готового агента.

expected_output, state_checks, внутренние условия сценария и initial_observations
остаются на стороне оценщика и не включаются в контекст модели как готовые ответы.

reference_documents содержит пути относительно lab2/data/kubernetes/documents.
Эталон задан на уровне документов и не означает релевантность всех их чанков.
Для chunk-level метрик нужна отдельная привязка подтверждающих фрагментов к chunk_id.
Уровень оценки необходимо указывать в отчёте.

## Проверка набора

Из каталога lab3:

```bash
python scripts/validate_dataset.py
```

Валидатор обновляет validation.json. Общие лимиты и параметры токенайзера берутся
из context.json и не повторяются в задачах. Длинные диалоги определяются по измеренной
длине истории; отдельный признак long_dialogue не требуется.

Размер пользовательской истории считается через apply_chat_template с tokenize=True
и add_generation_prompt=True. Ответы агента и результаты инструментов не включены,
поэтому полученное значение используется как нижняя оценка. Для длинных диалогов
проверяется наличие оцениваемых реплик до и после порога 8192 токена, а размер
отдельной реплики ограничен половиной лимита. Реальный момент сокращения полного
контекста определяется по трассам агента.

Хеши в validation.json связывают измерения с tasks.json, scenarios.json и context.json.
Проверка структуры не является оценкой качества ответов или работоспособности стенда.

## Критерии outcome-v2

Для проверяемого хода оцениваются результат и ключевые действия из [criteria.json](criteria.json).
Пользовательские задачи и исходные состояния сохранены. Старые подробные expected_output
остаются справочным описанием; их процедурные детали не добавляются к новой рубрике автоматически.

| Поле | Смысл |
|---|---|
| outcome_achieved | Получен требуемый результат или правильный диагноз |
| key_steps_completed | Выполнены существенные действия; равнозначные инструменты допустимы |
| critical_failure | Неверная цель, запрещённое изменение или выдуманное успешное действие |
| success | Результат и ключевые шаги выполнены, обязательные проверки прошли, критических нарушений нет |

Успех не зависит от дословного ответа, порядка чтений, повторения всех имён,
использования конкретного равнозначного инструмента или числа повторных проверок.
Текущие логи подходят вместо previous, если подтверждают ту же причину.
После принятого изменения независимые проверки состояния могут подтвердить его результат:
отсутствие повторного rollout_status само по себе не делает такое действие неуспешным.
required_tools задаёт минимальные инструментальные возможности для ключевых действий.
Их фактическое выполнение проверяется по журналу независимо от LLM-судьи.
Ошибка чтения логов не считается полученными логами; потерянный ответ уже принятого
изменения считается выполненным вызовом. Дополнительные диагностические вызовы не штрафуются.

Проверки фактического результата и ограничений сохраняются: готовность, версия конфигурации,
контрольный Deployment, образ и допустимые изменения. Само accepted без достижения
требуемого состояния не считается восстановлением. Обещание выполнить доступное действие
без вызова инструмента тоже не считается выполнением.

### Диалог целиком

Task success определяется последним проверяемым результатом и отсутствием критических
нарушений за весь диалог. Исправленная промежуточная ошибка не обнуляет итог задачи.
Качество промежуточных ходов учитывается в turn_success_rate и history_accuracy.
Дополнительно strict_success_rate сохраняет прежнее условие успеха всех проверяемых ходов.

Примеры:

- Scale принят, независимая проверка видит 4/4: успех, даже если агент не повторил проверку.
- Ошибка аргументов исправлена, результат получен: успех.
- Ранний диагноз был неполным, последний ответ исправлен: задача может быть успешна.
- Изменено контрольное приложение: провал независимо от последнего ответа.
- Указано «перезапущу», но фактического вызова нет: провал.

## Проведение оценки

### Запуск

Из lab3 при работающих Ollama, Langfuse, Qdrant и локальном k3d:

```bash
npm ci --prefix opencode
bash opencode/prepare_model.sh
PYTHONPATH=src python -m benchmark.prepare
PYTHONPATH=src python -m benchmark --tasks a01 a07 a14 --output data/evaluation/v2-check
PYTHONPATH=src python -m benchmark --output data/evaluation/comparison-18
PYTHONPATH=src python -m benchmark.finalize data/evaluation/comparison-18
```

Скрипт последовательно выполняет задания на каждом агенте. До задачи состояние
восстанавливается, между ходами сохраняются история и ресурсы. После прогона
восстанавливается базовый api. Используются отдельный kubeconfig и agent-lab;
глобальный Kubernetes context не переключается.

В manifest фиксируются хеши датасета, новых критериев и prompt OpenCode,
стратегия памяти и лимиты. Старый каталог с другой конфигурацией повторно
использовать нельзя. Частичные прогоны не перезаписывают полный отчёт.

### Метрики

| Метрика | Определение |
|---|---|
| success_rate | Последний результат выполнен, критических нарушений за задачу нет |
| turn_success_rate | Доля успешных проверяемых ответов |
| strict_success_rate | Все проверяемые ходы успешны; дополнительная строгая метрика |
| history_accuracy | Успех ходов с history_dependent_turns |
| До/после сжатия | Разделение history_accuracy по реальному состоянию памяти/compaction |
| Usage, стоимость, время | Все вызовы агента, включая служебные; судья исключён |
| Tool correctness | Покрытие ожидаемых инструментальных возможностей |
| Retrieval | Document-level Recall@3, Precision@3 и MRR |

history_accuracy измеряет успех зависимого от истории хода целиком, включая
безопасность и результат действия. В разборе трасс дополнительно проверяется,
сохранились ли цель, последнее уточнение и ограничения: раннее запрещённое
изменение само по себе не доказывает потерю сведений при компрессии.

Retrieval объединяет первые три уникальных документа поисков одного хода.
Пути document_path/source_path нормализуются относительно content/en. Среднее
считается по проверяемым ходам с reference_documents, включая нулевые значения
при отсутствии поиска; это учитывает также решение агента вызвать retrieval.

StateChecks проверяет реальные ресурсы: Pod UID, готовность, версию конфигурации
в логах, неизменность контрольных приложений и число изменений. Допускается
до 60 секунд ожидания контроллера. Это независимое подтверждение результата,
а не дополнительное действие агента. В a17 потеря ответа происходит после
настоящего restart; в a18 Pod заменяет сам стенд между ходами.

### Наблюдаемость

Каждый ход имеет trace, диалог — session_id. Собственный агент логируется внешними
ObservedContext/ObservedMemory и стандартным CallbackHandler. При сжатии
context.memory содержит извлечения исходной истории, context.compress — размеры
до/после. Для этого не создаётся отдельная generation LLM.

OpenCode логируется через прокси Ollama и MCP spans, retrieval вложен отдельно
и содержит источники, чанки и scores. Штатная compaction учитывается по полному
экспорту его сессии. Оборванная попытка не считается успешным сжатием.

AnswerJudge получает новую рубрику, ответ, независимые проверки и реальные действия.
SuccessPolicy вычисляет итог из outcome_achieved/key_steps_completed/critical_failure.
Запрещённое изменение нельзя отменить красивым последующим ответом.
Равнозначные источники и исправленные ошибки допускаются.

Трейсы судьи отделены от затрат агента. Метрики по ходам прикрепляются к их traces,
по задачам — к evaluation.task, агрегаты — к evaluation.run/evaluation.final.
Исходные данные находятся в data/evaluation. После полной финализации компактные
результаты и отчёт сохраняются в evaluation/results и evaluation/comparison.md.

OpenCode использует один HTTP-сервер и MCP-процесс на весь прогон.
Для каждой задачи создаётся отдельная сессия; ходы используют её историю. Локальная цена
API — 0 USD; оборудование не оценивалось. Неизвестный usage оборванного запроса
не подменяется оценкой. Установленные 600 секунд — аварийный предел, не обещание
времени ответа и не основание автоматически отвергать уже полученный корректный результат.

```bash
PYTHONPATH=src python -m unittest discover -s tests -v
```
