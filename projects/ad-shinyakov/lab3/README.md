# Диалоговый агент для Kubernetes

Лабораторная работа 3. Собственный агент построен на LangGraph и использует
retrieval из lab2, готовый Kubernetes MCP сервер и ограниченные операции с Deployment.
Набор из 18 заданий и описание стенда находятся ниже.

## Подготовка и запуск

Команды выполняются из каталога lab3. Требуются Docker, kubectl и Ollama
с исходной моделью glm4:9b. В lab2 должны быть подготовлены эмбеддинги и индекс Qdrant.

```bash
python -m pip install -r requirements.txt
bash scripts/cluster.sh up
bash scripts/cluster.sh deploy
docker compose -f ../lab2/compose.yaml up -d qdrant
bash scripts/prepare_model.sh
python scripts/prepare_mcp.py
PYTHONPATH=src python -m agent chat
```

prepare_model.sh создаёт glm4-agent:9b на существующих весах glm4:9b с шаблоном
нативных вызовов. Исходная модель сохраняется. JSON Schema ограничивает выход
вызовом инструмента с обязательными аргументами либо финальным ответом.
Вызовы разбирает Ollama; текстовые команды не исполняются.

prepare_mcp.py устанавливает kubernetes-mcp-server v0.1.2 с проверкой SHA256
и создаёт отдельный kubeconfig ServiceAccount agent. Скрипт рассчитан на текущий
macOS ARM64. Токен действует 24 часа; для обновления повторите команду.
Секретные данные и бинарник находятся в исключённом из Git каталоге data/.

Диалог сохраняется через SqliteSaver в data/dialogues.sqlite. Команды /new и /exit
начинают новый диалог и завершают приложение. Продолжение после перезапуска:

```bash
PYTHONPATH=src python -m agent chat --thread-id ID_ДИАЛОГА
```

CLI принимает --model и --thread-id. Параметры модели находятся в AgentConfig,
пути и таймауты инструментов — в ToolConfig. Обработчики запросов, управление
контекстом и структура графа описаны в [agent.md](docs/agent.md).

## Инструменты и контекст

Чтение ресурсов, списка подов, логов и событий выполняется через готовый
[containers/kubernetes-mcp-server](https://github.com/containers/kubernetes-mcp-server).
Он запускается дочерним процессом по stdio и закрывается вместе с сессией агента.
Для другого MCP-клиента точка запуска — bash scripts/kubernetes_mcp.sh.
MCP имеет отдельные учётные данные для agent-lab. Разрешены чтение и операции
масштабирования/обновления Deployment; exec, удаление, просмотр kubeconfig и Secrets
не предоставляются. Универсальные операции изменения скрыты от модели.

search_docs вызывает DocumentRetriever из lab2: тот же Qwen, префикс запроса,
артефакт ced08184c9da0803 и коллекция kubernetes_cbdea5c1950ecc44c1d9.
Повторная генерация ответа RAG не запускается. Возвращаются тексты, chunk_id,
источники и scores. Лимиты: 1–5 фрагментов, до 2000 символов каждый.

restart_deployment, scale_deployment и rollout_status — короткие методы поверх
того же MCP. Разрешены Deployment в agent-lab и масштабирование 1–5. Перезапуск
читает текущий ресурс и меняет аннотацию шаблона подов. rollout_status проверяет
текущую готовность без ожидания внутри инструмента. Облачный контекст не переключается.

Вход модели ограничен 8192 токенами. При переполнении старая история сокращается
до извлечений пользовательских сообщений и результатов инструментов, без вызова LLM.
Текущий ход сохраняется целиком; полная история и память остаются в SQLite. Промпты и описания инструментов находятся в prompts/.

## Постановка задачи

Локальный стенд k3d описан в [cluster.md](docs/cluster.md). Запуск из lab3:

```bash
bash scripts/cluster.sh up
bash scripts/cluster.sh deploy
bash scripts/cluster.sh status
```

Разворачивается базовый `api` с двумя репликами в `agent-lab`. Kubeconfig хранится
отдельно в `data/cluster/`. Сценарии для оценки реализованы в src/benchmark.

Предметная область — диагностика и восстановление приложений в Kubernetes.
Агент получает запрос пользователя, исследует состояние рабочей нагрузки,
обращается к документации и определяет допустимое действие. После изменения
проверяется состояние приложения: успешный ответ API на команду сам по себе
не подтверждает восстановление.

Задачи требуют совмещать сведения из документации и текущее состояние кластера.
Например, правило обновления переменных окружения из ConfigMap объясняет причину
устаревшей конфигурации, но факт применения новой версии определяется по логам
созданных Pod. При недоступном образе или неверном selector Service перезапуск
не устраняет причину неисправности. Корректным результатом такой задачи является
диагноз с указанием необходимой правки и ограничений доступных инструментов.

Предусмотрен собственный агент на LangGraph с retrieval из lab2. Для сравнения
OpenCode получает те же задания, инструменты и сведения о стенде.

## Условия выполнения

Сценарии рассчитаны на отдельный локальный кластер k3d. Рабочие нагрузки размещаются
в namespace `agent-lab`. Разрешены перезапуск Deployment и изменение числа реплик
в диапазоне от 1 до 5. Операции с нодами, ресурсами kube-system, произвольное
выполнение команд и чтение Secrets исключены из контракта стенда.

Ограничения определены для данного эксперимента и передаются обоим агентам.
Они не являются ограничениями Kubernetes. Запрос на диагностику не разрешает
изменение состояния; запрос на действие относится только к указанной цели.

В [scenarios.json](evaluation/scenarios.json) описаны 15 начальных состояний,
предусловия их подготовки и события между репликами. Это декларативные
спецификации. Приведённые наблюдения задают условия тестов и не представляют
результаты измерений в работающем кластере.

## Состав набора

Набор содержит 18 задач на русском языке. Основные группы: проверка состояния,
обновление конфигурации, масштабирование, диагностика ошибок запуска, уточнение
цели действия и восстановление после ошибки инструмента.

| Тип задания | Количество | Назначение |
|---|---:|---|
| Одиночный запрос | 9 | Работа с текущим состоянием, документацией и разрешёнными действиями |
| Короткий диалог | 7 | Использование предыдущих реплик, уточнений и результатов инструментов |
| Длинный диалог | 2 | Сохранение существенных сведений при сокращении истории |

По сложности выделены 3 задачи уровня easy, 7 — medium и 8 — hard. Уровень easy
предполагает явно заданную цель и ограниченное действие либо проверку состояния.
Medium требует сопоставления нескольких наблюдений или диагностики причины.
Hard включает неопределённый результат вызова, незавершённую операцию, неоднозначную
цель либо зависимость от удалённых реплик диалога.

Формулировки и критерии приведены в [каталоге заданий](evaluation/README.md#каталог-задач).
Полная последовательность входных реплик хранится в [tasks.json](evaluation/tasks.json).
[Описание формата](evaluation/README.md) определяет структуру данных и порядок проверки.

## Инструментальные возможности

Ниже приведены имена возможностей, используемые в разметке. При подключении через
MCP конкретные имена сервера сопоставляются с ними одинаково для обоих агентов.

| Инструмент | Назначение |
|---|---|
| `search_docs` | Поиск в корпусе lab2 с возвратом текстов, идентификаторов, источников и оценок близости |
| `inspect_workload` | Чтение Deployment, Pod, событий, probes и связанных Service/EndpointSlices |
| `get_pod_logs` | Чтение ограниченного объёма текущих или предыдущих логов контейнера |
| `restart_deployment` | Инициирование управляемого перезапуска указанного Deployment |
| `scale_deployment` | Изменение количества реплик в разрешённом диапазоне |
| `rollout_status` | Разовая проверка завершения операции; повторное ожидание организует агент |

Таблица задаёт контракт инструментов для реализации агента. В разметке указаны
необходимые возможности, но не фиксированная последовательность всех вызовов.
Выбор порядка действий и дополнительных проверок остаётся за агентом.

## Проверка работы с историей

Для эксперимента задан лимит входного контекста агента 8192 токена. Размер окна
модели составляет 32768 токенов, максимальный выход — 2048. Каждый длинный диалог
содержит 15 пользовательских реплик. В первых двух задаются основная цель,
ограничения или причина неисправности; последняя реплика требует использовать
эти сведения после обсуждения архивных отчётов других приложений.

| Задача | Проверяемая зависимость | Токенов в пользовательской части истории |
|---|---|---:|
| a23 | Последняя согласованная цель масштабирования вместо прежнего значения | 15960 |
| a24 | Установленная причина сбоя и ограничение доступных способов исправления | 15985 |

Измерения получены токенайзером GLM с применением шаблона диалога. В расчёт включены
только пользовательские сообщения; ответы модели, описания инструментов и их
результаты отсутствуют. Значения служат нижней оценкой размера истории. Даже она
превышает выбранный лимит, тогда как отдельная реплика занимает не более 1326 токенов.
Момент фактического сокращения полного контекста определяется при выполнении агента.

## Критерии успешности

Для каждой проверяемой реплики заданы ожидаемый результат, необходимые
инструменты и проверки состояния `state_checks`. Критерии успешности включены
в текст `expected_output`; зависимые от истории реплики отмечены номерами
в `metadata.history_dependent_turns`. Задача считается выполненной,
если требования соблюдены, необходимое состояние подтверждено наблюдениями и
отсутствуют запрещённые побочные изменения. Дословное совпадение с эталонным текстом
не требуется.

В диалогах дополнительно проверяются связи с предыдущими репликами: выбранный объект,
исходные параметры, последнее уточнение пользователя и результат нештатного вызова.
Ограничения контракта и проверяемые сведения должны сохраняться при сокращении истории.

## Проверка набора

Из каталога lab3:

```bash
python -m pip install -r requirements.txt
python scripts/validate_dataset.py
```

Валидатор проверяет структуру задач, соответствие эталонов и state_checks
номерам реплик, отметки зависимости от истории, идентификаторы сценариев,
имена инструментов и длины
пользовательской части длинных диалогов. Результат сохраняется в
[validation.json](evaluation/validation.json) вместе с хешами входных файлов.

Общие параметры подсчёта хранятся отдельно в [context.json](evaluation/context.json).
Используется `AutoTokenizer` для `zai-org/glm-4-9b-chat-hf`, ревизия
`8599336fc6c125203efb2360bfaf4c80eef1d1bf`, с `trust_remote_code=False`.
При первом обращении требуются файлы токенайзера из Hugging Face. При наличии кеша
проверка выполняется с `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1`.

Результат валидации подтверждает структуру и размеры входных данных. Качество
ответов, выполнение действий и обработка переполнения контекста оцениваются
отдельно при запуске агентов на подготовленном стенде.
